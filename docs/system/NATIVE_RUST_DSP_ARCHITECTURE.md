# Native Rust DSP & Neural Sidecar Architecture

This specification details Nullherz's technical rationale and architectural design for maintaining a **100% Native Rust DSP, Sidecar, and Neural Execution Engine**, contrasting it with JavaScript/Python runtime alternatives.

## Executive Rationale

High-performance real-time audio systems operating at 32–64 sample block quanta (0.67–1.33 ms processing budgets at 48 kHz) require deterministic audio callback guarantees. Managed runtimes (JavaScript/V8, Python/CPython) suffer from intrinsic architectural limitations that make them unsuitable for real-time DSP host engines or zero-latency insert sidecars:

1. **Garbage Collection & JIT Stalls:** Non-deterministic GC pauses (5–50 ms) in V8/Python cause immediate audio buffer underruns (xruns) and audio dropouts.
2. **Interpreter Locks & FFI Overhead:** CPython's Global Interpreter Lock (GIL) and JS/V8 FFI marshaling introduce multi-microsecond memory copy overhead per audio quantum.
3. **Memory Layout Control:** Managed runtimes cannot guarantee 64-byte alignment required for AVX2 / AVX-512 / WASM SIMD 128-bit vectorization on local arrays.

## Core Architecture Invariants

### 1. Deterministic Real-Time Audio Execution
- **Zero Allocations:** The real-time audio execution path (`SignalProcessor::process`) performs zero heap allocations (`Vec::new()`, `Box::new()`).
- **Zero Locking:** Synchronization between control/neural workers and real-time audio threads uses lock-free atomic queues (`ShmRingBuffer`, SPSC rings) and `ShmSignal` atomic pointer swaps.
- **Zero Syscalls:** File I/O, networking, and system calls are strictly forbidden in the RT audio callback.

### 2. Hardware SIMD Acceleration & Padé Neural Approximants
Native Rust compiles vector DSP directly to CPU registers using `audio_dsp::simd_vec::FloatX16` and `wide::f32x4`.
- **Padé Neural Activations:** Non-linear neural activation functions (such as `tanh` and GELU for TCN neural saturation and State-Space Model dynamic EQs) are evaluated in SIMD registers using Padé rational approximants (`tanh_simd`), avoiding dynamic FFI calls or C++ engine context switches.

### 3. Lock-Free Zero-Copy Shared Memory (SHM)
- Intra-machine sidecar processes communicate through memory-mapped, 64-byte aligned `AudioBlock` ring buffers prefaulted during allocation.
- `SidecarHost` and `SidecarContext` handle incoming audio blocks and commands directly in shared memory without intermediate serialization or FFI array copying.

### 4. Composite In-Place Execution (`SidecarStore` & `SidecarChain`)
To prevent multi-hop IPC ring buffer latency accumulation (which adds 1 quantum delay per separate sidecar hop):
- `SidecarStore` provides a composite container (`SidecarChain`) that encapsulates an optional instrument sidecar followed by sequential insert sidecars in a single execution loop within the same sidecar process.
- Audio generated by the instrument passes through sequential insert DSP in-place across double-buffered ping-pong scratch buffers (`scratch_a`, `scratch_b`) in <0.1 ms CPU time within a single block quantum.
- `SidecarChain` presents a **single IPC boundary** to the audio host engine, maintaining deterministic <1ms real-time latency across arbitrarily deep effect chains.

## Metadata Schema & Tag-Based Query System

Every sidecar module in `SidecarStore` registers a `SidecarDescriptor` containing searchable metadata and tags:

```rust
pub struct SidecarDescriptor {
    pub id: String,
    pub name: String,
    pub sidecar_type: SidecarType,
    pub tags: Vec<String>,
    pub description: String,
    pub latency_samples: usize,
}
```

### Supported Tag Categories
- `"delay"`: Time-based delay lines, tape echo, multi-tap delay.
- `"neural"`: Machine learning / Padé approximant TCNs and hypernetwork dynamic filters.
- `"insert"`: In-line DSP processors attached to channel, bus, or master inserts.
- `"real-time"`: Zero-allocation, sub-millisecond real-time execution safety.
- `"instrument"`: MIDI-driven synthesis engines and sample generators.
- `"eq"`: Multi-mode state-variable filters, parametric EQs, and dynamic equalizers.

## Sidecar Directory Structure

Standalone executable sidecars live inside the `sidecars/` directory as dedicated workspace member crates:

```
sidecars/
├── algorithmic-delay/      # Low-latency tape delay with Hermite interpolation
├── algorithmic-eq/         # State-Variable Filter EQ (LP, HP, BP, Notch)
├── algorithmic-synth/      # Dual-oscillator MIDI synthesizer instrument
├── neural-filter/          # Hypernetwork dynamic filter with SIMD non-linearities
├── neural-saturation/      # Padé SIMD neural analog saturation processor
├── nullherz-broadcast/     # UDP/TCP audio stream mirroring sidecar
├── nullherz-dummy/         # Reference test sidecar
├── nullherz-midi/          # Low-latency SHM MIDI injection sidecar
├── nullherz-sampler/       # Direct memory-mapped disk sampler sidecar
├── nullherz-template/      # Boilerplate template for custom SDK sidecars
├── reference_dsp/          # Baseline DSP validation sidecar
└── spectral-transfuser/    # DNA latent space frequency-domain transfuser
```

By maintaining a **pure native Rust architecture**, Nullherz achieves:
1. Sub-millisecond (<1ms) real-time audio latency across 4-deck DJ performance, live routing, and Ableton-like composition graphs.
2. Complete elimination of GC and interpreter stalls.
3. Unified, latency-free composite sidecar processing chains.
